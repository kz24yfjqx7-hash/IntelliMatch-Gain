### 算法必须是真的，禁止硬编码假曲线

这是本项目最大的加分项——答辩现场评委可能会要求改数据重跑，曲线必须真的跟着变。

**FedAvg**（`fedavg.py`）：4 个节点各持一份本地负荷预测数据（`gen_datasets.py` 生成，故意做成非独立同分布，让联邦训练有意义）。每轮各节点用 NumPy 训练一个小 MLP（如 8-16-1），服务端按样本量加权平均参数。loss 和 acc 是真实计算出来的。

**差分隐私**（`dp.py`）：梯度先按 L2 范数裁剪，再加真实高斯噪声 `N(0, (C·σ)²)`。用矩会计或简化的 `ε = q·√(T·log(1/δ))/σ` 累计隐私预算，每轮返回真实的 `epsilonSpent`。预算耗尽时在响应里返回 `anomaly`（后端会据此生成 R05 高危告警）。

**Top-k**（`topk.py`）：真的按梯度绝对值取前 k 比例，其余置零，返回真实压缩率 `(1 - k/n)·100`。

**DQN**（`dqn.py` + `train_dqn.py`）：自建储能调度环境——状态 `[pv, load, soc, price, hour]`，动作 `[charge, idle, discharge]`，奖励 = 削峰收益 − 越限惩罚 − 电价成本。用 NumPy 手写 Q 网络（两层 MLP）+ 经验回放训练几千步，checkpoint 存 `models/dqn.npz`。服务启动时加载，推理时返回真实 Q 值。约束校验（SOC 20%~95%、单节点最大 30kW）要真的做，越限动作要被拦下来并记录到 `constraintsChecked.violations`。

**分类分级**（`classifier.py`）：k-means 聚类 + 规则加权（敏感字段、采集粒度、数据量），输出 L1~L4。这块替代原来 `raspi/src/services/scientificCompute.js` 里的浏览器端 Pyodide 方案。

### DeepSeek 三级降级是硬性要求

答辩现场大概率没有可靠网络。`adapters/deepseek.py` 必须：

```
真实 API 调用（超时 8 秒）
  ↓ 失败
命中 cache/deepseek_cache.json（按 scene + context 哈希做 key）
  ↓ 未命中
规则化模板文本（用上下文数据填空，保证语句通顺可读）
```

**永远返回 HTTP 200，永远有 `answer`**，用 `source` 字段标记来源（`live`/`cache`/`rule`）。`scripts/warm_cache.py` 在答辩前联网跑一次，把常见场景的真实回答灌进缓存。

`DEEPSEEK_API_KEY` 为空时直接跳过 live 阶段。

### 2.4 必须删掉 Pyodide

`raspi/src/services/scientificCompute.js:34` 从 `cdn.jsdelivr.net` 动态加载 Pyodide，这违反「完全离线运行」的验收标准，断网即失效，而且树莓派 4B 跑 WebAssembly Python 很吃力。

**处理方式**：删除整个 Pyodide 加载逻辑，把 `scientificCompute.js` 改写成调用后端 API 的薄客户端（`POST /assets/classify`、`POST /risk/assess`），对外方法签名尽量保持不变，减少调用方改动。

```

│   └── docker.service

```

### 四个关键点

**1. 双架构交叉构建。** 在 x86 开发机上用 `docker buildx` + QEMU 一次出两个架构：

```bash
docker run --privileged --rm tonistiigi/binfmt --install all
docker buildx create --name energy-builder --use --bootstrap
```

前端 Dockerfile 的 node 构建阶段用 `FROM --platform=$BUILDPLATFORM node:20-alpine AS builder`（跑本机原生速度），只有 nginx 运行阶段需要目标架构——因为 `npm run build` 产出的静态文件与架构无关。

`build.sh` 开头必须先验证基础镜像的 arm64 可用性（命令见规范文档第 1.2 节）。**如果 `mysql:8.0` 没有 arm64 变体，两个架构一起换成 `mariadb:11`**，DDL 完全兼容，队友的 SQL 一行都不用改。

导出镜像时**必须用 `--output type=docker,dest=xxx.tar` 直接输出 tar 文件**，不要走「build → load 到本地 → save」那条路——buildx 的多架构镜像没法直接 `docker save`，本地守护进程也存不下两个同名同 tag 的不同架构镜像。基础镜像（mysql/redis）分架构拉取时会互相覆盖，必须**串行** pull → save → rmi，不要并行。详见规范文档 2.4 节的三个坑。

**2. Docker 本身要打进包里。** 目标机可能没装 Docker，离线环境不能 `apt install`。`build.sh` 从 `download.docker.com/linux/static/stable/<arch>/` 下载静态二进制（约 60MB）放进 `docker/` 目录，`install.sh` 检测到没有 Docker 时自动解压安装并 `systemctl enable --now docker`。每个包只带自己架构的那一份。

**3. `install.sh` 严格按规范文档第四节的九步实现**，重点：

- 第 2 步架构校验必须包含 **`armv7l` 拒绝逻辑**——树莓派刷成 32 位系统时 `uname -m` 返回 `armv7l`，`mysql:8.0` 没有 armv7 镜像，必须立即退出并提示重刷 64 位系统。这是最容易翻车的地方，别让它跑到一半才失败。
- 第 7 步生成 `.env` 时，MySQL 密码和 `JWT_SECRET` 必须**随机生成**（`openssl rand -hex 32`），不能所有安装实例共用同一个密钥，那是会被安全审查挑出来的明显缺陷。
- 每一步失败都要打印**可操作的**错误提示，不要只吐堆栈。端口被占就列出占用进程，包损坏就提示重新拷贝。

**4. 树莓派内存必须调优。** 4GB 机型上，桌面 + Chromium + 五个容器合计约 2.0~2.3GB，没什么余量。三件必做的事：

- `mysql-arm64.cnf` 里 **`performance_schema = OFF`**（单这一条省 200~400MB，最关键）、`innodb_buffer_pool_size = 128M`
- docker-compose 给 mysql / algo-service / backend 加 `memory` 上限
- `install.sh` 检测到 ARM 时把 swap 调到 2GB

另外 ARM 包的种子数据可以减半（30 天历史指标降到 7 天），页面照样有内容，初始化快很多。

DQN 权重在 x86 开发机上训练好、打进镜像，**树莓派只做推理，绝不在树莓派上训练**。
