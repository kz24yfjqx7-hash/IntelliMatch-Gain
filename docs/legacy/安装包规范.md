# Linux 离线安装包规范 v1.0

> 目标：**两套**完全离线的一键安装包，目标机可以没有 Docker、没有网络。
>
> | 产物 | 目标机 | 用途 |
> |---|---|---|
> | `energy-tds-v1.0-linux-x86_64.tar.gz` | x86_64 服务器 / 笔记本 | 云端主平台 |
> | `energy-tds-v1.0-linux-arm64.tar.gz` | 树莓派 4B（64 位系统） | 边缘节点 / 现场演示 |

---

## 一、架构红线（最容易翻车的地方）

### 1.1 树莓派必须是 64 位系统

树莓派 4B 硬件是 ARM64，但**如果刷的是 32 位 Raspberry Pi OS，系统跑在 armv7l 模式下，`mysql:8.0` 根本没有 armv7 镜像**，整个方案直接死掉。

开工前先在树莓派上执行：

```bash
uname -m
# aarch64  → 正确，继续
# armv7l   → 必须重刷 64 位系统（Raspberry Pi OS 64-bit）
```

`install.sh` 第一步就要做这个检查，遇到 `armv7l` 立即退出并打印重刷系统的提示，不要让它跑到一半才失败。

### 1.2 基础镜像的 arm64 可用性必须先验证

构建 ARM 包之前，逐个验证基础镜像是否有 arm64 变体：

```bash
for img in mysql:8.0 redis:7-alpine python:3.11-slim nginx:alpine; do
  echo -n "$img : "
  docker buildx imagetools inspect $img 2>/dev/null | grep -c "linux/arm64" || echo "❌ 无 arm64"
done
```

`mysql:8.0` 的 arm64 支持在部分版本上有过反复。**如果验证失败，整体换成 `mariadb:11`**——DDL 语法完全兼容，`contract/DB-SCHEMA.md` 里的建表脚本一行都不用改，镜像还小 200MB，arm64 支持一直很稳。改的话两个架构一起改，不要一个用 MySQL 一个用 MariaDB。

## 二、构建流程

### 2.0 先理解一件事：安装包里装的是镜像，不是源码

```
  开发机（联网）                                  目标机（离线）
  ─────────────────────────────────             ──────────────────
  源码 ──docker build──> 镜像                    tar.gz
         ──docker save──> 镜像 tar               ──> docker load
         ──下载 docker 二进制──┐                 ──> docker compose up
         ──复制 sql/配置/脚本──┤
                              └──> tar.gz  ═══>
```

**目标机上不做任何编译**。`npm install`、`pip install`、`docker build` 全部发生在开发机上。所以打包这一步必须联网，而且必须在**两人代码都合并到一起之后**执行——`build.sh` 要同时读到 `backend/`、`algo-service/`、`frontend/` 三个目录。

### 2.1 一次性环境准备（开发机上只做一次）

```bash
docker run --privileged --rm tonistiigi/binfmt --install all   # QEMU 模拟器，让 x86 机器能构建 arm64
docker buildx create --name energy-builder --use --bootstrap
```

开发机要求：Docker 20.10+、能联网、**磁盘剩余 25GB 以上**（两个架构的中间层加起来很占地方）。

### 2.2 构建命令

```bash
sudo ./packaging/build.sh --arch all        # 两个架构都出
sudo ./packaging/build.sh --arch amd64      # 只出 x86_64
sudo ./packaging/build.sh --arch arm64      # 只出树莓派
```

产物落在 `dist/`：

```
dist/
├── energy-tds-v1.0-linux-x86_64.tar.gz
├── energy-tds-v1.0-linux-x86_64.tar.gz.sha256
├── energy-tds-v1.0-linux-arm64.tar.gz
└── energy-tds-v1.0-linux-arm64.tar.gz.sha256
```

### 2.3 build.sh 内部十步

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 前置检查 | docker / buildx / 网络 / 磁盘 25GB / `backend/` `algo-service/` `frontend/` 三个目录都在 |
| 2 | 验证基础镜像 arm64 可用性 | 见 1.2 节；`mysql:8.0` 不可用就整体换 `mariadb:11` |
| 3 | 训练 DQN | `models/dqn.npz` 不存在时跑 `train_dqn.py`，**只在 x86 原生跑一次**，产物两个架构共用 |
| 4 | 预热 DeepSeek 缓存 | 有 `DEEPSEEK_API_KEY` 时跑 `warm_cache.py`，把常见场景的真实回答灌进 `cache/` |
| 5 | 构建三个自建镜像 | backend / algo-service / frontend，每个架构一遍 |
| 6 | 拉取两个基础镜像 | mysql / redis，按架构分别拉 |
| 7 | 导出镜像 tar 并 gzip | 见下面的坑 |
| 8 | 下载 Docker 静态二进制 | 从 `download.docker.com/linux/static/stable/<arch>/`，只带当前包的架构 |
| 9 | 组装目录 | 复制 `install.sh` `uninstall.sh` `config/` `systemd/` `部署说明.md`，以及从 `backend/sql/` 复制建表脚本 |
| 10 | 打 tar.gz + 生成 SHA256 | 写入 `VERSION` 文件记录版本、架构、构建时间、各镜像摘要 |

### 2.4 三个必须绕开的坑

**坑 A：buildx 的多架构镜像没法直接 `docker save`。**

buildx 构建多架构清单时默认要求推到 registry，本地 Docker 守护进程也存不下两个同名同 tag 的不同架构镜像。**正确做法是用 `--output type=docker,dest=` 直接输出成 tar 文件**，跳过本地镜像库：

```bash
docker buildx build \
  --platform linux/arm64 \
  --output type=docker,dest=build/images/backend-arm64.tar \
  -t energy-tds/backend:1.0 \
  ./backend
```

这样两个架构互不干扰，也不需要 `docker load` 再 `docker save` 绕一圈。

**坑 B：基础镜像分架构拉取会互相覆盖。**

`docker pull --platform linux/arm64 mysql:8.0` 会把本地的 `mysql:8.0` 覆盖成 arm64 版本。所以两个架构必须**串行**处理，每轮结束清掉：

```bash
for arch in amd64 arm64; do
  docker pull --platform linux/$arch mysql:8.0
  docker save mysql:8.0 | gzip > build/images/mysql-$arch.tar.gz
  docker rmi mysql:8.0
done
```

不要图快并行跑，会拿到错误架构的镜像，而且要装到目标机上才会暴露。

**坑 C：ARM 构建慢，但可以优化到能忍。**

QEMU 模拟下 arm64 构建比原生慢很多。两个已经做掉的优化：

- 所有 Python 依赖（numpy、cryptography、bcrypt、pymysql、gmssl）在 PyPI 上都有 **aarch64 预编译 wheel**，`pip install` 直接下二进制不编译。前提是 `requirements.txt` 里不引入需要现场编译的包。
- 前端 Dockerfile 的 node 构建阶段用 `--platform=$BUILDPLATFORM` 跑本机原生速度，因为 `npm run build` 产出的 `dist/` 与架构无关，只有 nginx 运行阶段需要目标架构：

```dockerfile
FROM --platform=$BUILDPLATFORM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

### 2.5 时间与空间预算

| 项 | 首次 | 改代码后重build |
|---|---|---|
| x86_64 包 | 10~15 分钟 | 3~5 分钟（层缓存命中） |
| arm64 包 | 25~40 分钟 | 8~15 分钟 |
| DQN 训练 | 3~10 分钟 | 跳过（checkpoint 已存在） |
| 开发机磁盘占用 | 峰值约 25GB | 构建完可 `docker buildx prune` 回收 |

**每次改代码都要重新跑 build.sh**，没有增量打包的说法。所以别等到答辩前一天才第一次打包——建议 W3 就先打一次空跑，把流程本身的问题暴露出来。

## 四、install.sh 必须做的九步

按顺序执行，任何一步失败立即退出并打印可操作的错误信息（不要只打印堆栈）：

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 检查 root 权限 | 提示用 `sudo ./install.sh` |
| 2 | 检查 `uname -m` 与包架构一致 | 打印"本包为 arm64，当前机器为 x86_64，请使用对应安装包" |
| 3 | 检查内存 ≥ 3.5GB、磁盘 ≥ 8GB | 打印实际值与要求 |
| 4 | 检测 Docker；没有则从 `docker/` 离线安装并 `systemctl enable --now docker` | 打印手动安装指引 |
| 5 | 检测端口 80 / 8000 / 8100 / 3306 / 6379 占用 | 列出占用进程，提示改 `.env` 里的端口变量 |
| 6 | `docker load` 全部镜像，校验 SHA | 提示包可能损坏，重新拷贝 |
| 7 | 生成 `/opt/energy-tds/.env`：**随机生成** MySQL 密码和 `JWT_SECRET`，其余照 `.env.example` | — |
| 8 | `docker compose up -d`，轮询 `http://localhost/api/v1/health`，最长等 180 秒 | 超时则打印 `docker compose logs --tail=50` |
| 9 | 安装 systemd 单元并 enable，打印访问地址 + 六个演示账号 | — |

第 7 步的随机密钥很重要——所有安装实例共用同一个 `JWT_SECRET` 是明显的安全缺陷，验收方如果做安全审查会被指出来。

安装成功的输出应该长这样：

```
════════════════════════════════════════════
  能源可信数据空间平台  安装完成
════════════════════════════════════════════
  访问地址   http://192.168.1.100
  演示账号   admin / admin123        系统管理员
             grid / grid123          电网调度方
             vpp / vpp123            虚拟电厂运营商
             subject / subject123    能源主体
             regulator / reg123      监管方
             edge / edge123          边缘节点

  服务管理   systemctl start|stop|status energy-tds
  查看日志   docker compose -f /opt/energy-tds/docker-compose.yml logs -f
  卸载       sudo /opt/energy-tds/uninstall.sh
════════════════════════════════════════════
```

`uninstall.sh` 要停服务、删容器镜像、删 systemd 单元，但**默认保留数据卷**，加 `--purge` 才删数据。

## 五、树莓派 4B 内存预算（4GB 机型）

这是 ARM 包能不能跑起来的决定性因素。实测量级：

| 组件 | 内存 | 备注 |
|---|---|---|
| Raspberry Pi OS 64-bit 桌面版 | ~500MB | 用 Lite 版可省 300MB |
| Chromium 全屏 kiosk | 600~900MB | 大头，无法避免 |
| MySQL 8.0（**调优后**） | ~350MB | 不调优是 550~700MB |
| Redis | ~30MB | |
| backend | ~150MB | |
| algo-service（NumPy） | ~250MB | |
| nginx | ~15MB | |
| **合计** | **≈ 2.0~2.3GB** | 4GB 机型可行，但没什么余量 |

### 必须做的三件事

**1. MySQL 调优**（`config/mysql.cnf`，ARM 包专用低配版）：

```ini
[mysqld]
performance_schema        = OFF      # 单这一条省 200~400MB，最关键
innodb_buffer_pool_size   = 128M
innodb_log_file_size      = 32M
innodb_flush_log_at_trx_commit = 2   # 演示场景，减少 SD 卡写入
max_connections           = 50
table_open_cache          = 200
tmp_table_size            = 16M
max_heap_table_size       = 16M
```

**2. docker-compose 里加内存上限**，防止某个服务吃爆整机：

```yaml
services:
  mysql:        { deploy: { resources: { limits: { memory: 512M } } } }
  algo-service: { deploy: { resources: { limits: { memory: 400M } } } }
  backend:      { deploy: { resources: { limits: { memory: 300M } } } }
```

**3. 把 swap 调到 2GB**（`install.sh` 检测到 ARM 时自动做）：

```bash
sed -i 's/^CONF_SWAPSIZE=.*/CONF_SWAPSIZE=2048/' /etc/dphys-swapfile
systemctl restart dphys-swapfile
```

### 两个建议

- **能用 USB SSD 就别用 SD 卡**。MySQL 跑在 Class 10 SD 卡上写入延迟很高，而且高频写入会加速卡损坏。答辩前一天卡坏了是很常见的事故。
- **ARM 包的种子数据可以减半**（30 天历史指标降到 7 天），页面照样有内容，数据库初始化能快很多。

## 六、开机自启

```ini
# systemd/energy-tds.service
[Unit]
Description=Energy Trusted Data Space Platform
Requires=docker.service
After=docker.service network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/opt/energy-tds
ExecStart=/usr/bin/docker compose up -d
ExecStop=/usr/bin/docker compose down
TimeoutStartSec=300

[Install]
WantedBy=multi-user.target
```

ARM 包额外装一个 kiosk 单元：等平台健康检查通过后，用 `chromium-browser --kiosk --noerrdialogs --disable-infobars http://localhost` 全屏拉起，满足原《开发任务清单》里"开机自启 + 全屏 Kiosk 展示"的验收项。注意加 `--disable-gpu-compositing` 之类的参数缓解树莓派上的渲染卡顿。

## 七、体积预算

| 项 | 未压缩 | gzip 后 |
|---|---|---|
| mysql:8.0 | ~600MB | ~180MB |
| python:3.11-slim ×2（backend + algo） | ~800MB | ~260MB |
| nginx:alpine + 前端静态文件 | ~60MB | ~25MB |
| redis:7-alpine | ~40MB | ~15MB |
| Docker 离线二进制 | ~120MB | ~110MB |
| **单个包合计** | ~1.6GB | **≈ 600MB** |

换 `mariadb:11` 可再省约 90MB（压缩后）。两个包加起来约 1.2GB，U 盘拷贝没问题，网盘传输建议分卷。

## 八、安装包验收清单

**必须在一台干净机器上验证**——开发机上一定是能跑的，那不算数。

1. 找一台**从未装过 Docker** 的 Linux 机器，**拔掉网线**
2. U 盘拷入 tar.gz，解压，`sudo ./install.sh`
3. 全程无任何联网请求（可用 `tcpdump` 或直接物理断网确认）
4. 2 分钟内安装完成，打印访问地址和账号
5. 浏览器打开，`admin/admin123` 登录成功
6. 跑通 `contract/API-CONTRACT.md` 第六部分的 12 条业务链路
7. `reboot`，开机后服务自动起来，页面可访问（ARM 包还要验证 Chromium 自动全屏）
8. `sudo ./uninstall.sh` 卸载干净，`docker ps -a` 无残留容器
9. **ARM 包必须在真实树莓派上跑一遍**，不能只用 QEMU 验证——内存和 SD 卡 IO 的问题只有真机才暴露
