### 7.3 剩余风险与遗留（2026-08-22 口径；2026-08-23 的遗留清单见 §8.5）

1. **`algo_fl_round.loss` 的列型迁移需人工执行一次（唯一硬遗留）**。B-011 的修法是把该列从 `DECIMAL(10,6)` 改为 `DOUBLE`：
   - `backend/sql/01_schema.sql` 已经是 `DOUBLE`，**全新部署（含 docker compose 首次启动、离线安装包）自动生效，无需任何额外操作**；
   - 但**当前这个已经初始化过的开发/联调库还没执行该 DDL**（本机安全策略禁止测试与修复 Agent 执行 `ALTER TABLE`）。存量库必须由人工执行一次
     `backend/sql/03_migrate_20260822.sql`（同一脚本还包含 `chain_evidence_backup` 建表，该表后端在缺失时会自动创建，属兜底）：
     ```bash
     docker compose exec -T mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" energy_tds < backend/sql/03_migrate_20260822.sql
     ```
   - 未执行迁移时的可见后果：算法返回的 loss 为 kW² 量级 MSE，一旦 ≥ 10000，该轮 `algo_fl_round` 落库报 `1264 Out of range value for column 'loss'`，整轮进度既不落库也不上链 → 前端收敛曲线缺轮、`rounds[].evidenceId` 缺失。本轮复测用的演示参数下 loss 远小于 10000，故 TC-38-07 等用例未再命中该缺陷，**不代表已在存量库上修复**。
2. 存量库里在缺陷修复轮**之前**绑定的 ECC/RSA 密钥是随机串占位，验签必然 false、托管代签会降级返回 None（不 500）（2026-08-23 复核本联调库：`did_key` 中全部 10 把非 SM2 密钥经曲线点/模数校验均为真实密钥，**当前库无占位密钥，无需处理**；该条仅适用于其它在修复轮前建的存量库）。演示前建议重新导库，或对这些 DID 执行一次 `rotate-key`。存量老数据的 `updated_at` 仍是按 UTC 写入的旧值，本轮不回填。
3. 链状态增量校验保留一处理论残余风险：构造一次 CRC32 普通和与加权和同时碰撞的改动可骗过「要不要重算」这一步（需针对性构造）。单条 `/evidence/verify`、凭证导出、任何一次新块写入引起的重算都会立刻暴露它；想彻底关闭这层缓存，把 `_table_fingerprint()` 返回 `None` 即可退回全量校验。
4. TC-311-OS（端侧 Modbus/RS485/MQTT 采集、MQTT + TLS 1.3 传输、断网本地缓存续传）**仍为阻塞**，理由不变：本环境无端侧设备与 MQTT Broker，契约只定义前后端 HTTPS + WebSocket，树莓派边缘采集程序不在本次交付内。替代验证仍是 TC-33-05 / TC-39-07 / TC-38-03。
5. `node_info` 的四个实时指标列会在有 WebSocket 客户端连接时被 5 秒周期改写（B-021 的设计内行为，保证「推送值 == 库里的值」）。按固定指标值断言的用例需要注意；离线节点不参与游走。

### 8.2 本轮新发现缺陷：R03 高频权限变更告警丢失（接口与安全 §4 B-014）

- **现象**：接口与安全专项 API-AUD-23「同一主体 5 次权限变更 → 出现 R03_PERM_CHURN 告警」失败，`GET /audit/alerts` 返回 `[]`（"无 R03"）。同时回收 / 驳回权限的请求明显变慢。
- **证据**（后端日志 `scratchpad/backend.log`，UTC 时间；数据库只读查询）：
  - 02:58:06 `INSERT audit_alert … alert_id='al-000061', rule_code='R03_PERM_CHURN'`；02:58:15（**9 秒后**）才打出「【风控告警】R03_PERM_CHURN 高频权限变更」；
  - 只读查询 `audit_alert`：自增 **id 67 空洞**（66 → 68），`al-000061` 这个编号后来被 10:58:17 的一条 R01 告警复用——即 R03 那行被回滚了；本轮 R03 在库里一条都没有。
- **根因**（`backend/modules/audit/rules.py::fire` / `_create_alert`、`modules/permission/service.py::_log_change → fire_perm_change`）：
  1. `_create_alert` 另开会话上链，而请求事务刚 `write_evidence` 过、链尾行锁在手 → 自锁，3 s 锁超时 × 3 次重试 = 请求多挂 9 秒；
  2. 上链失败后 `run_with_retry` 的 rollback 把同一会话刚插的 `audit_alert` 行一起回滚 → 告警丢失；
  3. Redis 去重标记 `risk:alerted:R03_PERM_CHURN:<did>` 在落库**之前**就种下 → 该主体在 10 分钟窗口内再触发也不再告警，且无人知道。
  与 §6.4 的 200 秒自锁是同一类坑（审计/告警写链与业务事务争链尾行锁）。
- **修法**（未提交，后端 2026-08-23 11:29 重启生效）：`fire(..., db=)` 透传请求会话，告警与存证走同一连接、不自行 commit（保住 `run_with_retry` 的整段重放语义）；去重标记改为**落库成功后**再种。
- **新增单测**（`backend/tests/test_audit.py`，3 条，均通过）：`test_R03借请求会话落告警且不自行提交`、`test_告警落库失败不会把规则静默整个窗口`、`test_五次申请驳回经接口触发R03并上链`。backend pytest 337/337。
